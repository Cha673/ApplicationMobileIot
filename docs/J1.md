# J1 — Du capteur au téléphone

## Questions à résoudre

### Qui produit la mesure, qui la transporte, qui la conserve et qui l'affiche ?

- **Produit** : le capteur simulé (`simulator`) mesure température et CO₂ et publie sur MQTT.
- **Transporte** : le broker Mosquitto route les messages MQTT jusqu'au backend.
- **Conserve** : le backend insère les mesures dans PostgreSQL via `PgMeasurementRepository`.
- **Affiche** : l'application mobile React Native interroge l'API REST et affiche les valeurs.

### Pourquoi une API et un broker ont-ils des rôles différents ?

Le broker MQTT est orienté **flux** : il diffuse les messages en temps réel à tous les abonnés mais ne conserve pas l'historique. Il est adapté aux capteurs qui publient en continu.

L'API REST est orientée **requête** : elle répond à la demande du client, lit l'état courant depuis PostgreSQL et peut fournir un historique. Elle découple le rythme des capteurs du rythme du mobile.

### Qu'affiche le téléphone pendant le chargement ou si aucune mesure n'existe ?

- **Chargement** : un `ActivityIndicator` (spinner) avec le texte "Chargement des salles…" est affiché tant que la requête n'a pas abouti.
- **Aucune mesure** : la carte de la salle affiche "Aucune mesure disponible" à la place des valeurs numériques.
- **Erreur API** : un écran d'erreur affiche le message d'erreur HTTP et un bouton "Réessayer".

## Jalons

### ✅ Une variation du simulateur atteint le téléphone en passant par le backend

**Scénario** : lancer `docker compose up -d --build --wait`, observer les logs du backend, puis ouvrir l'app mobile.

**Preuve** (commande reproductible) :
```sh
# 1. Démarrer la stack
docker compose up -d --build --wait

# 2. Vérifier que le backend reçoit et stocke les mesures
docker compose logs backend | grep telemetry
# → [telemetry] saved: sensor-001 T=22.14°C CO2=912ppm

# 3. Vérifier l'API
curl http://localhost:3000/api/rooms | python3 -m json.tool
# → latestMeasurement.temperature et co2 présents
```

### ✅ L'équipe peut retrouver le même objet à chaque étape

L'identifiant `sensor-001` est traçable à chaque étape :
- **MQTT** : topic `campus/v1/devices/sensor-001/telemetry`
- **Log backend** : `[telemetry] saved: sensor-001`
- **PostgreSQL** : `SELECT device_id, temperature FROM measurements WHERE device_id = 'sensor-001' ORDER BY observed_at DESC LIMIT 1;`
- **API** : `curl http://localhost:3000/api/rooms/salle-203` → `"deviceId": "sensor-001"`
- **Mobile** : carte "Salle 203" affiche la mesure du sensor-001

### ✅ Le mobile gère le chargement et une erreur d'API

- État **chargement** : spinner + texte affiché à l'ouverture de l'app.
- État **erreur** : couper le backend (`docker compose stop backend`), rafraîchir l'app → écran rouge avec message d'erreur et bouton Réessayer.
- État **vide** : salle sans mesure → "Aucune mesure disponible".

## État réel du projet

**Fonctionne**
- Stack Docker complète : Mosquitto, simulateur, PostgreSQL, backend.
- Backend reçoit et stocke les mesures MQTT avec déduplication par `message_id`.
- API REST expose `/api/rooms`, `/api/rooms/:id`, `/api/rooms/:id/history`, `/api/health`.
- App mobile affiche liste des salles, mesures, loading et erreur.

**Incomplet ou en échec**
- App mobile non testée sur téléphone physique (nécessite `npm install` dans `mobile/` et configuration de l'IP du backend).
- Pas de détail par salle accessible depuis la liste (navigation basique implémentée).

**Limites ou dette connue**
- Polling mobile toutes les 5 s (pas de push temps réel).
- Pas de cache offline côté mobile (J2).
- La fraîcheur n'est pas visualisée explicitement (J2).

**Prochaine priorité**
- Installer les dépendances mobile et tester sur Expo Go.
- Ajouter le cache offline (AsyncStorage) pour J2.
- Gérer les doublons et mesures retardées côté backend (J2).
