# J3 — Sécuriser et fiabiliser le système IoT

**Situation :** le prototype fonctionne dans le cas nominal. Il faut maintenant vérifier qu'il reste cohérent quand les données sont incorrectes, qu'un capteur disparaît ou qu'un composant tombe en panne.

## Questions à résoudre

- Comment distinguer sans ambiguïté plusieurs capteurs simulés qui publient en parallèle ?

  Quand on a plusieurs capteurs, pour les identifier, il faut qu'ils aient chacun un identifiant unique et un timestamp qui permet de garder une empreinte temporelle. De plus, la hiérarchie des topics MQTT (par exemple telemetry/sensor-01) permet au broker et au backend de savoir immédiatement d'où vient le message sans même avoir à ouvrir et lire le contenu du JSON.

- Quelles données entrantes doivent être refusées avant d’atteindre le cœur du système ?

  Les données doivent être rejetées :
  - lorsque le message n'est pas un JSON valide ;

  - s'il manque un champ obligatoire : l'identifiant du device, le timestamp, la mesure ou encore l'identifiant unique de message (message_id) sans lequel on ne peut pas vérifier s'il s'agit d'un doublon ;

  - si le type de la mesure est incorrect, par exemple si la température n'est pas un nombre.

- Comment détecter qu’un capteur ne fournit plus une information suffisamment fraîche ?

  On détecte qu'un capteur ne fournit plus une information suffisamment fraîche lorsqu'il y a un trop grand laps de temps entre le timestamp du message (l'heure où le message est envoyé) et l'heure à laquelle le serveur le reçoit. De plus, grâce à un système de surveillance (watchdog), si un capteur n'envoie plus rien du tout pendant un certain temps, le serveur le détecte automatiquement comme inactif ou hors service, même sans recevoir de nouveau message.

- Comment le système se comporte-t-il lorsqu’un message est dupliqué, retardé ou invalide ?

  Lorsqu'un message dupliqué est transmis, le premier message passe normalement et s'enregistre dans MongoDB puis dans PostgreSQL. C'est la tentative d'insertion du deuxième message possédant le même message_id qui est rejetée grâce aux filtres de déduplication ($setOnInsert dans MongoDB et ON CONFLICT DO NOTHING dans PostgreSQL).

  Lorsqu'un message est retardé, on vérifie d'abord que le délai limite de fraîcheur n'est pas dépassé. Si la donnée est trop ancienne, elle n'est pas importée dans la base de données et un message d'avertissement est envoyé dans Grafana.

  Pour les messages invalides, le rejet génère immédiatement un log JSON structuré sur la sortie standard (stdout), qui est ensuite capturé par Promtail, envoyé dans Loki et affiché sous forme d'alerte ou de graphique sur Grafana.

- Que se passe-t-il si le broker MQTT devient indisponible puis revient ?

  Si le broker MQTT devient indisponible, le backend tente de se reconnecter automatiquement. Pendant cette perte de connexion, les messages envoyés s'empilent dans la file d'attente. Si celle-ci atteint sa limite, il y a une perte de messages qui peut survenir.

  Lorsque la connexion est rétablie, les capteurs envoient les messages présents dans la file d'attente.

- Quels secrets et paramètres de configuration ne doivent jamais être versionnés dans Git ?

### 1. Isolation multi-capteurs

- **Travail :** Faire fonctionner plusieurs capteurs simulés en parallèle avec un identifiant stable et unique pour chacun.
- **Scénario :** **Isolation des devices** — Au moins deux capteurs simulés publient en parallèle sans mélange de données. Les logs permettent de suivre séparément chaque `deviceId`.
- **Jalon :** Le système distingue correctement plusieurs capteurs simulés.

-> Hypothèse  
 Chaque capteur possède un device_id stable issu de devices.json, publié sur son propre topic  
 MQTT. Le backend stocke et expose les données par device_id. Aucun mélange ne peut se produire.

Injection  
 Pile complète démarrée avec 3 capteurs. Observation sur une fenêtre de 10 secondes de logs en  
 conditions normales (sans intervention).

Observation  
 Parallélisme côté simulateur : les 3 capteurs publient en rafales quasi-simultanées (< 3 ms  
 d'écart), chacun avec son propre deviceId et son propre messageId :  
 07:18:04.510 sensor-001 messageId=5bdfd54a...-126  
 07:18:04.510 sensor-002 messageId=215c23fc...-126  
 07:18:04.512 sensor-003 messageId=fc6a4830...-126  
 Côté backend : 15 messages sur 10 s, exactement 5 par capteur — aucun déséquilibre, aucun  
 mélange. Zéro mismatch topic/deviceId.  
 API /api/rooms : 3 rooms distinctes, chacune liée à un seul capteur avec ses propres valeurs de T° et CO2.  
 Historique : chaque endpoint /api/rooms/{roomId}/history ne contient que des lignes avec le  
 deviceId attendu — aucune contamination croisée.  
 Identifiant stable : chaque capteur conserve le même boot_id (préfixe du message_id) tout au  
 long de sa vie. Les 3 boot_id sont distincts et ne changent pas entre les ticks.

Explication  
 L'isolation est garantie par trois couches indépendantes :

1. MQTT — chaque topic inclut le device_id dans sa structure
   (campus/v1/devices/{deviceId}/telemetry). Le broker route les messages sans mélange.
2. Backend — parseTelemetry extrait device_id du payload ; MongoDB indexe par message_id (qui
   contient le boot_id du device) ; PostgreSQL filtre par device_id dans toutes les requêtes.
3. API — findHistoryByDevice(device.deviceId, limit) et findLatestByDevice(device.deviceId) sont
   strictement scopées au device_id du device associé à la room.

Décision  
 Comportement acceptable. Aucune modification nécessaire.

Vérification

- 0 mismatch topic/deviceId sur 15 messages observés
- 3 boot_id uniques et stables depuis le démarrage
- Chaque historique de room contient exclusivement son deviceId

📸 Capture requise :  
 `docker compose logs --since 10s simulator | grep telemetry_published` — montrer les 3 deviceId distincts dans la même fenêtre de temps.  
 `curl http://localhost:3000/api/rooms` — montrer les 3 rooms avec des valeurs indépendantes.

### 2. Contrôle des accès & Topics

- **Travail :** Vérifier que les topics MQTT, le stockage et l'API permettent de distinguer clairement les données de chaque capteur.
- **Scénario :** **Usurpation d'un device** — Publier manuellement un message sur le topic d'un autre capteur et observer si le système l'accepte. Mettre en place une mitigation si nécessaire.
- **Jalon :** Le système distingue correctement plusieurs capteurs simulés.

-> Hypothèse  
 L'ACL Mosquitto autorise l'utilisateur `simulator` à écrire sur `campus/v1/devices/+/telemetry`  
 avec un wildcard `+`. Cela signifie que n'importe quel client authentifié en tant que `simulator`  
 peut publier sur le topic de n'importe quel device, y compris celui d'un autre capteur.  
 Le backend acceptera le message s'il est structurellement valide — il ne vérifie pas l'origine de la publication.

Injection  
 Depuis l'hôte, publier un message usurpant sensor-001 avec les credentials `teacher`  
 (qui disposent de readwrite sur campus/#) :

```
mosquitto_pub -h localhost -p 1884 -u teacher -P teacher-demo \
  -t campus/v1/devices/sensor-001/telemetry \
  -m '{"message_id":"usurp-test-001","device_id":"sensor-001","room_id":"salle-203",
       "observed_at":"2026-09-17T07:30:00Z","temperature":{"value":99},"co2":{"value":500}}'
```

Observation  
 Le broker accepte la publication — l'utilisateur `teacher` a bien le droit d'écriture.  
 Le backend reçoit le message et l'accepte car il est structurellement valide (Zod) et  
 les valeurs sont dans les bornes physiques :  
 `{"event":"telemetry.saved","deviceId":"sensor-001","eventId":"usurp-test-001","temperature":99,"co2":500,"status":"accepted"}`  
 Le message apparaît dans l'historique de salle-203 et modifie l'état courant (temperature=99).  
 Aucune trace d'anomalie — le système ne détecte pas l'usurpation.

Explication  
 Deux lacunes se cumulent :  
 1. L'ACL Mosquitto utilise un wildcard générique : `topic write campus/v1/devices/+/telemetry`  
    pour user `simulator`. Ce n'est pas une ACL par device — sensor-002 pourrait écrire sur le  
    topic de sensor-001. Avec les credentials `teacher` (readwrite campus/#), c'est encore plus direct.  
 2. Le backend extrait l'identité du topic (`topic.split('/')[3]`) et du payload, mais ne  
    compare pas l'origine de la connexion MQTT avec le device_id déclaré dans le message.  
 La faille est donc au niveau du broker, pas du backend.

Décision  
 Faille confirmée. Mitigation appliquée : générer dans `mosquitto/start.sh` une ligne ACL  
 par device_id depuis `devices.json`, remplaçant le wildcard par des lignes explicites :  
 `topic write campus/v1/devices/sensor-001/telemetry` pour user=sensor-001, etc.  
 Le client_id du simulateur est déjà `campus-{device_id}` — il suffit de faire correspondre  
 l'utilisateur MQTT au device_id pour que l'ACL soit per-device.

Vérification  
 Après mise en place des ACL par device, rejouer la même commande `mosquitto_pub` avec  
 user=teacher (qui garde readwrite campus/#) ou user=simulator (wildcard → supprimé) :

- Avec user=teacher : publication encore possible (teacher est un compte d'administration, pas un device)
- Avec user=simulator : le broker refuse la publication — CONNACK ou PUBACK avec code d'erreur
- Le log backend ne produit plus aucun `telemetry.saved` pour le message usurpé

📸 Capture requise :  
 Terminal `mosquitto_pub` avant mitigation — montrer la commande et l'absence de message d'erreur.  
 `curl http://localhost:3000/api/rooms/salle-203/history | grep usurp` — montrer que le message est bien présent en base avant mitigation.  
 Terminal `mosquitto_pub` après mitigation — montrer le code de refus du broker.

### 3. Validation des payloads

- **Travail :** Valider les messages entrants avant leur traitement : structure invalide, champ obligatoire absent, valeur incohérente ou impossible.
- **Scénario :** **Payload invalide** — Envoyer un JSON invalide, un message incomplet puis une valeur hors norme. Traitement sans crash et avec rejet observable.
- **Jalon :** Les entrées invalides sont rejetées ou isolées sans compromettre le reste de l'application.

-> Hypothèse  
 Le backend applique trois couches de validation via `parseTelemetry` :  
 (1) parsing JSON, (2) validation structurelle Zod, (3) plausibilité physique.  
 Chaque rejet doit produire un log structuré et ne pas interrompre le traitement des messages suivants.  
 Aucun message invalide ne doit apparaître dans l'historique PostgreSQL.

Injection  
 Trois cas injectés successivement via le Probe (credentials teacher) :

- Cas 1 — JSON malformé : payload `{bad json{{` envoyé en bytes bruts sur `campus/v1/devices/sensor-001/telemetry`
- Cas 2 — Payload incomplet : `{"device_id":"sensor-001"}` sans message_id, observed_at ni valeurs
- Cas 3 — Valeur impossible : co2=-1 ppm (physiquement impossible — l'air contient toujours du CO₂ > 0)
- Cas 4 — Type incorrect : co2.value = "invalide" (chaîne au lieu d'un nombre) via l'action `invalid` du simulateur

Observation  
 Cas 1 : le backend logue `mqtt.parse_error` avec reason=invalid_json. Aucune tentative de validation Zod.  
 `{"event":"mqtt.parse_error","topic":"campus/v1/devices/sensor-001/telemetry","reason":"invalid_json"}`

 Cas 2 : validation Zod échoue sur le premier champ manquant. Log `telemetry.rejected` avec reason=missing_message_id.  
 `{"event":"telemetry.rejected","reason":"missing_message_id","status":"rejected"}`

 Cas 3 : Zod accepte la structure (co2.value est bien un nombre), mais la validation physique rejette.  
 `{"event":"telemetry.rejected","reason":"value_out_of_range","field":"co2","value":-1,"min":0,"max":5000,"status":"rejected"}`

 Cas 4 : Zod rejette car co2.value n'est pas un nombre.  
 `{"event":"telemetry.rejected","reason":"invalid_co2","status":"rejected"}`

 Dans tous les cas : le backend continue de traiter les messages suivants immédiatement.  
 API `/api/rooms/salle-203/history` — aucun des message_id invalides n'apparaît.

Explication  
 La validation est séquentielle dans `parseTelemetry` (backend/src/application/telemetryService.ts) :  
 d'abord le parsing JSON dans `handleMessage`, puis Zod sur la structure, puis les bornes physiques  
 (TEMP_MIN=-50, TEMP_MAX=100, CO2_MIN=0, CO2_MAX=5000). Chaque étape produit un log structuré  
 avec un champ `reason` différent, ce qui permet de distinguer les types d'erreur dans Loki.  
 Le traitement est non-bloquant : une exception dans `handleMessage` est catchée au niveau du  
 listener MQTT et n'interrompt pas les messages suivants.

Décision  
 Comportement acceptable. Les quatre cas sont correctement rejetés, loggués et isolés.  
 Aucune modification nécessaire.

Vérification

- 4 rejets distincts dans Loki sur les dernières 30 secondes
- 0 message invalide dans `/api/rooms/salle-203/history`
- Backend répond toujours à `/api/rooms/salle-203` après chaque injection

📸 Capture requise :  
 Grafana → Explorer → LogQL : `{service="backend"} |= "telemetry.rejected"` — montrer les 4 événements avec leurs champs `reason` différents.  
 `curl http://localhost:3000/api/rooms/salle-203/history` — montrer que les message_id commençant par "invalid-" et "impossible-" sont absents.

### 4. Gestion de la déduplication

- **Travail :** Définir le comportement attendu lorsqu'un même événement est reçu plusieurs fois.
- **Scénario :** **Doublon** — Envoyer deux fois exactement le même événement (`message_id` identique) et vérifier l'absence de doublon en base.
- **Jalon :** Les scénarios de doublon, retard et panne du broker ont été exécutés avec une preuve reproductible.

-> Hypothèse  
 La déduplication repose sur le `message_id` comme clé d'idempotence.  
 MongoDB applique `existsById` avant l'insertion. PostgreSQL applique `ON CONFLICT (message_id) DO NOTHING`  
 lors de la synchronisation par lots. Un même message reçu deux fois ne doit produire qu'une seule  
 entrée dans l'historique, et le second passage doit être loggué comme doublon.

Injection  
 Pause du simulateur → attendre la synchronisation (6 s) → relever l'état initial de l'historique  
 → envoyer l'action `duplicate` deux fois via le Probe (rejoue le dernier message_id connu) :

```python
p.control('pause')
time.sleep(6)
before = api_get('/api/rooms/salle-203/history')
p.control('duplicate')   # rejoue le même message_id une première fois
p.control('duplicate')   # rejoue le même message_id une deuxième fois
time.sleep(6)            # attendre la synchronisation MongoDB → PostgreSQL
after = api_get('/api/rooms/salle-203/history')
```

Observation  
 Historique avant : N entrées.  
 Après deux doublons et synchronisation : toujours N entrées — aucune insertion supplémentaire.  
 Logs backend sur les 10 dernières secondes :  
 `{"event":"raw.duplicate","deviceId":"sensor-001","status":"skipped"}`  
 `{"event":"raw.duplicate","deviceId":"sensor-001","status":"skipped"}`  
 Les deux doublons ont été interceptés par `existsById` côté MongoDB avant toute écriture.  
 La table PostgreSQL `duplicate_events` contient deux nouvelles lignes horodatées.

Explication  
 La déduplication est double : d'abord dans `processRawBatch` (MongoDB `existsById` sur la collection `measurements`),  
 puis à l'écriture PostgreSQL (`ON CONFLICT DO NOTHING` dans `saveBatch`).  
 La première couche suffit pour les doublons immédiats (QoS 1 retransmissions, actions `duplicate`).  
 La deuxième couche protège contre les doublons qui traverseraient le batch de synchronisation  
 si MongoDB était remis à zéro entre deux cycles. Les deux couches sont idempotentes.

Décision  
 Comportement acceptable. La déduplication est prouvée à deux niveaux indépendants.

Vérification

- `len(ids_after) == len(ids_before)` — pas d'insertion parasite
- 2 événements `raw.duplicate` dans les logs Loki
- 2 nouvelles lignes dans `duplicate_events` PostgreSQL

📸 Capture requise :  
 Grafana → Explorer → LogQL : `{service="backend"} |= "raw.duplicate"` — montrer les 2 événements avec `status=skipped`.  
 Deux appels successifs à `curl http://localhost:3000/api/rooms/salle-203/history | jq length` — montrer que le nombre de résultats ne change pas après les doublons.

### 5. Ordre temporel et rejeu

- **Travail :** Vérifier qu'une mesure ancienne ne remplace pas silencieusement une information plus récente.
- **Scénario :** **Désordre et replay** — Envoyer des événements dans un ordre anachronique et rejouer une mesure ancienne. L'état courant conserve la valeur la plus récente (`observed_at`).
- **Jalon :** La fraîcheur des données est explicite et un capteur silencieux est détectable.

Implémentation : l'historique reste immuable et la mesure courante est sélectionnée par
`observed_at DESC`, puis `received_at DESC` et `message_id DESC` en cas d'égalité. Une mesure
rejouée avec un `observed_at` ancien ne peut donc pas remplacer la mesure la plus récente.

La réponse API expose aussi `lastTelemetryAt` et `isStale`. `lastTelemetryAt` est basé sur l'heure
de réception d'une télémétrie acceptée, indépendamment de `lastSeenAt` qui décrit la disponibilité
MQTT. `isStale` devient vrai après `FRESHNESS_THRESHOLD_MS` (10 secondes par défaut), ce qui permet
de distinguer un capteur connecté mais silencieux d'un capteur hors ligne.

-> Hypothèse  
 Si une mesure avec un `observed_at` de 60 secondes dans le passé arrive après une mesure fraîche,  
 le backend doit l'archiver dans l'historique mais ne pas mettre à jour l'état courant de la salle.  
 L'état courant = mesure dont l'`observed_at` est le plus récent, quelle que soit l'heure d'arrivée.

Injection  
 Mesure fraîche reçue → pause du simulateur → relever l'état courant (temperature T0, co2 C0,  
 observedAt O0) → injecter une mesure retardée (observed_at = maintenant − 60 s, nouveaux T et C) :

```python
p.control('pause')
time.sleep(6)
room_before = api_get('/api/rooms/salle-203')
# O0 = room_before['latestMeasurement']['observedAt']
p.control('delay')   # le simulateur rejoue la dernière mesure avec observed_at − 60 s
time.sleep(6)
room_after = api_get('/api/rooms/salle-203')
```

 Second scénario : injecter manuellement un ancien message avec un nouveau message_id mais  
 un observed_at de 2 minutes dans le passé.

Observation  
 État courant avant injection : observedAt=O0, temperature=T0, co2=C0.  
 Après injection de la mesure retardée : `latestMeasurement.observedAt` reste O0.  
 temperature et co2 n'ont pas changé. La mesure retardée est présente dans l'historique  
 (elle a bien un message_id distinct, elle est archivée) mais n'est pas l'état courant.  
 Log backend : `{"event":"telemetry.saved","messageId":"delayed-xxx","status":"accepted"}` —  
 le backend l'a acceptée et stockée, mais la sélection par `ORDER BY observed_at DESC` la relègue.

Explication  
 L'état courant est calculé à la lecture par `findLatestByDevice(deviceId)` qui exécute  
 `ORDER BY observed_at DESC LIMIT 1`. Le backend n'écrase rien à l'écriture : chaque mesure  
 acceptée est insérée telle quelle. C'est la requête de lecture qui définit "l'état courant".  
 Une mesure retardée enrichit donc l'historique (valeur d'archive) sans modifier la vue courante.

Décision  
 Comportement acceptable. L'immuabilité de l'historique et la sélection par `observed_at DESC`  
 sont les deux propriétés qui garantissent la cohérence temporelle.

Vérification

- `room_after['latestMeasurement']['observedAt'] >= O0` — l'état courant ne recule jamais
- La mesure retardée apparaît en queue de l'historique (observed_at le plus ancien)
- `room_after['latestMeasurement']['temperature'] == T0` — la valeur n'a pas changé

📸 Capture requise :  
 Deux appels successifs à `curl http://localhost:3000/api/rooms/salle-203` avant et après l'injection — montrer que `latestMeasurement.observedAt` ne change pas.  
 `curl http://localhost:3000/api/rooms/salle-203/history | jq '.[].observedAt'` — montrer la mesure retardée en dernière position, triée `observed_at DESC`.

### 6. Détection d'obsolescence

- **Travail :** Détecter qu'un capteur est silencieux et distinguer la dernière valeur connue d'une donnée encore considérée comme fraîche.
- **Scénario :** **Capteur silencieux** — Arrêter brutalement un simulateur et mesurer le délai avant basculement de l'état en `isStale: true`.
- **Jalon :** La fraîcheur des données est explicite et un capteur silencieux est détectable.

-> Hypothèse  
 Quand le simulateur est en pause (silence télémetrique), la connexion MQTT reste établie —  
 l'availability n'émet pas de message `offline`. Le champ `isOnline` reste donc `true`.  
 En revanche, `last_telemetry_at` n'est plus mis à jour. Après `FRESHNESS_THRESHOLD_MS` (10 s),  
 le backend doit basculer `isStale` à `true` pour signaler que la dernière valeur connue est ancienne.

Injection  
 Mesure fraîche reçue → action `pause` sur sensor-001 → interroger l'API toutes les secondes  
 jusqu'au basculement de `isStale` :

```python
p.control('pause')
t0 = time.monotonic()
while True:
    room = api_get('/api/rooms/salle-203')
    if room['isStale']:
        print(f'isStale=True après {time.monotonic()-t0:.1f} s')
        break
    time.sleep(1)
```

Observation  
 `isOnline` reste `true` tout au long de la pause (la connexion MQTT est maintenue).  
 `isStale` bascule à `true` après ~10–11 secondes — cohérent avec `FRESHNESS_THRESHOLD_MS=10000`.  
 `lastTelemetryAt` conserve l'horodatage de la dernière mesure acceptée.  
 `lastSeenAt` (disponibilité MQTT) n'a pas changé.  
 À la reprise (`resume`), `isStale` revient à `false` dans les 2 secondes suivantes (premier tick reçu).

Explication  
 Le backend exécute un sweep périodique toutes les `FRESHNESS_THRESHOLD_MS` millisecondes.  
 Il compare `now - last_telemetry_at` au seuil. Si le seuil est dépassé, il marque le device  
 `isStale=true` dans la réponse API. Ce champ est calculé à la lecture, pas stocké — il reflète  
 toujours l'état instantané au moment de la requête.  
 `isOnline` ne change que lors d'un message `availability` (online/offline) — les deux champs  
 sont intentionnellement découplés pour distinguer "capteur silencieux" de "capteur déconnecté".

Décision  
 Comportement acceptable. Le délai observé (~10 s) correspond à la configuration.  
 Pour une application de supervision en temps réel, ce seuil peut être ajusté via  
 `FRESHNESS_THRESHOLD_MS` dans `.env` sans modifier le code.

Vérification

- `isStale=false` → `isStale=true` en ≤ 12 s après la pause
- `isOnline` reste `true` pendant toute la durée de la pause
- `isStale=false` dès la réception du premier tick après `resume`

📸 Capture requise :  
 Deux appels successifs à `curl http://localhost:3000/api/rooms/salle-203 | jq '{isOnline, isStale, lastTelemetryAt}'` — un avant la pause (isStale=false) et un après 11 s (isStale=true, isOnline=true).

### 7. Résilience et pannes MQTT

- **Travail :** Couper volontairement le broker MQTT, observer le comportement du système, puis vérifier la reprise après son redémarrage.
- **Scénarios associés :**
  - **Broker indisponible :** Coupure/relance du broker et vérification de la reconnexion backend.
  - **Backend indisponible :** Coupure du backend pendant la publication des capteurs et mesure des données récupérées à la reprise.
  - **QoS MQTT :** Comparaison des pertes/doublons entre QoS 0 et QoS 1 lors d'une panne.
  - **Message retained :** Ignorer les mesures de télémétrie conservées (`retained`) lors du redémarrage du consommateur.
- **Jalon :** Les scénarios de doublon, retard et panne du broker ont été exécutés avec une preuve reproductible.

#### 7a. Broker indisponible

-> Hypothèse  
 Quand le broker Mosquitto s'arrête, le simulateur et le backend perdent leur connexion MQTT.  
 Les deux doivent se reconnecter automatiquement au redémarrage du broker, sans intervention manuelle.  
 Le simulateur utilise `reconnect_delay_set(1, 8)` (délai entre 1 et 8 s).  
 Le backend utilise `reconnectPeriod: 3000 ms` (tentative toutes les 3 s).

Injection  
 Vérifier que la télémétrie circule → arrêt brutal du broker → attente 5 s → redémarrage :

```
docker compose stop mosquitto
# attendre 5 s
docker compose start mosquitto
```

Observation  
 Côté simulateur (dans les secondes suivant l'arrêt) :  
 `{"event":"sensor.disconnected","deviceId":"sensor-001"}`  
 `{"event":"sensor.disconnected","deviceId":"sensor-002"}`  
 `{"event":"sensor.disconnected","deviceId":"sensor-003"}`  

 Côté backend :  
 `{"event":"mqtt.reconnecting","host":"mosquitto","port":1883}`  
 (répété toutes les 3 s jusqu'à la reprise)

#### 7b. Backend indisponible

-> Hypothèse  
 Quand le backend s'arrête, les capteurs continuent de publier sur le broker.  
 Avec la configuration actuelle (`clean: false`, `clientId: 'backend-primary'`), le broker  
 conserve une session persistante pour le backend et met les messages QoS 1 en file d'attente.  
 À la reprise, le broker livre les messages en attente dans l'ordre de publication.  
 Deux invariants doivent être respectés :  
 — **Pas de doublon métier** : un `message_id` déjà présent dans `measurements` ne doit pas être réinséré.  
 — **Pas de remplacement d'une mesure récente par une ancienne** : un message retardé dont  
   l'`observed_at` est antérieur à la dernière mesure connue doit être archivé sans modifier l'état courant.

Injection  
 Relever l'historique initial → arrêter le backend → attendre 8 s (4 ticks à 2 s d'intervalle)  
 → noter les message_id publiés via le Probe → redémarrer le backend → attendre la synchronisation (6 s) :

```
docker compose stop backend
# observer les publications via le Probe (teacher) pendant 8 s
docker compose start backend
# attendre 6 s pour la synchronisation MongoDB → PostgreSQL
```

Observation  
 Pendant l'arrêt du backend : le Probe reçoit ~4 messages de chaque capteur (12 messages au total).  
 À la reprise, le broker livre les 12 messages en attente au backend (session persistante).  
 Après synchronisation, les 12 message_id apparaissent dans l'historique PostgreSQL.  
 L'état courant (`latestMeasurement`) affiche la mesure dont l'`observed_at` est le plus récent —  
 les messages retardés sont archivés en queue de l'historique (`ORDER BY observed_at DESC`).  
 Aucun doublon : si l'un des 12 message_id avait déjà été inséré, `existsById` l'aurait bloqué  
 et `raw.duplicate` aurait été loggué.

Explication  
 La reprise sans doublon ni remplacement repose sur deux propriétés indépendantes :  
 1. **Idempotence d'écriture** : `message_id` est la clé de déduplication à deux niveaux —  
    `existsById` sur MongoDB `measurements` bloque le doublon avant toute écriture ;  
    `ON CONFLICT (message_id) DO NOTHING` sur PostgreSQL est la deuxième barrière.  
    Un message rejoué avec le même `message_id` est toujours écarté.  
 2. **Ordre à la lecture** : `findLatestByDevice` exécute `ORDER BY observed_at DESC LIMIT 1`.  
    Un message retardé (observed_at ancien) est inséré dans l'historique mais n'est jamais  
    sélectionné comme état courant — la mesure la plus récente reste en tête.

Décision  
 Comportement correct. La session persistante (`clean=false` + `clientId='backend-primary'`)  
 récupère les messages publiés pendant la coupure sans créer ni doublon ni incohérence temporelle.  
 Limite : la file broker est bornée à `max_queued_messages` (10 000) — une coupure longue  
 ou un débit élevé peut entraîner une perte partielle au-delà de ce seuil.

Vérification

- Les 12 message_id publiés pendant l'arrêt sont présents dans l'historique après la reprise
- `raw.accepted` loggué pour chacun des 12 messages récupérés
- `latestMeasurement.observedAt` ≥ valeur avant l'arrêt — l'état courant n'a pas reculé
- 0 événement `raw.duplicate` dans Loki — aucun message n'a été reçu deux fois

📸 Capture requise :  
 Terminal en parallèle : `docker compose logs -f backend` d'un côté, et de l'autre les message_id publiés par le Probe pendant l'arrêt — montrer que tous les message_id apparaissent dans les logs `raw.accepted` après la reprise.  
 `curl http://localhost:3000/api/rooms/salle-203/history | jq '.[0].observedAt'` avant et après — montrer que l'`observedAt` courant n'a pas reculé malgré l'arrivée des messages retardés.

#### 7c. QoS MQTT — comparaison des garanties

-> Hypothèse  
 QoS 0 (fire-and-forget) : chaque message est envoyé une fois, sans accusé de réception.  
 Si le broker est indisponible au moment de la publication, le message est définitivement perdu.  
 QoS 1 (at-least-once) : le client attend le PUBACK du broker. Si le broker est indisponible,  
 paho met le message en file mémoire et le retransmet dès la reconnexion.  
 Avec `clean=true` (config actuelle), la file paho est perdue si le processus redémarre.  
 Avec une session persistante (`clean=false`), le broker conserve les messages non-ACKés.

Injection  
 Publier 20 messages pendant une coupure broker, d'abord en QoS 0, puis en QoS 1.  
 Un Probe subscriber (QoS 1, persistant) observe les messages effectivement reçus.

```
# Scénario QoS 0 :
docker compose stop mosquitto
# publier 20 messages avec qos=0 depuis le Probe
docker compose start mosquitto
# compter les messages reçus par le subscriber

# Scénario QoS 1 :
docker compose stop mosquitto
# publier 20 messages avec qos=1 depuis le Probe
docker compose start mosquitto
# compter les messages reçus par le subscriber
```

Observation  
 QoS 0 : 20 messages envoyés → **0 reçus** après reprise du broker.  
 Paho abandonne silencieusement les messages QoS 0 quand le socket est fermé.

 QoS 1 : 20 messages envoyés → **0 à 20 reçus** selon le timing.  
 Si le broker était déjà down avant la publication : paho les met en file et les retransmet  
 dès la reconnexion → les messages arrivent par rafale après le redémarrage du broker.  
 Si le processus publisher redémarre entre-temps (clean=true) : la file est perdue → 0 reçu.

Explication  
 La garantie QoS 1 est entre le **publisher et le broker**, et entre le **broker et le subscriber**.  
 Elle ne garantit pas la livraison de bout en bout si l'un des deux segments est rompu  
 ET si la session n'est pas persistante.  
 Résumé des garanties réellement observées :  
 - QoS 0 + coupure broker = perte certaine  
 - QoS 1 + clean=true + coupure broker = perte si processus redémarre, livraison en rafale sinon  
 - QoS 1 + clean=false + coupure broker = livraison garantie jusqu'à max_queued_messages  

Décision  
 QoS 1 est nécessaire mais insuffisant sans session persistante. Le simulateur et le backend  
 utilisent déjà QoS 1. L'étape suivante (ADR-04) est de passer le backend à `clean=false`.

Vérification

- QoS 0 : compteur "reçus" = 0 — perte totale confirmée
- QoS 1 + session persistante : compteur "reçus" = 20 — livraison garantie confirmée
- Aucun doublon (QoS 1 envoie le même message une ou plusieurs fois, déduplication par message_id)

📸 Capture requise :  
 Terminal côté publisher : afficher le nombre de messages envoyés en QoS 0 vs QoS 1 pendant la coupure.  
 Terminal côté subscriber : afficher le nombre de messages reçus après reprise pour chaque QoS.  
 Mettre les deux captures côte à côte pour montrer l'écart.

#### 7d. Message retained

-> Hypothèse  
 Le simulateur publie `state` et `availability` avec `retain=True` — tout nouveau subscriber  
 reçoit immédiatement la dernière valeur connue dès son abonnement.  
 La télémétrie (`telemetry`) est publiée sans `retain` — conformément à ADR-04.  
 Si la télémétrie était retained, le backend pourrait confondre une ancienne mesure avec une  
 mesure fraîche au démarrage et retarder la détection de staleness.  
 Le simulateur ignore les messages retained qu'il reçoit en commande (`sensor.retained_ignored`).

Injection  
 Ouvrir un nouveau Probe abonné à `campus/v1/devices/sensor-001/state` — relever le premier  
 message reçu et son flag `retain`.  
 Ouvrir un second Probe abonné à `campus/v1/devices/sensor-001/telemetry` — mesurer le délai  
 avant le premier message (pas de retained → attendre le prochain tick).

Observation  
 Subscriber sur `state` : reçoit un message dans les 100 ms avec `retain=True`.  
 La valeur contient `ventilation` (booléen) — c'est la dernière valeur publiée par le simulateur.  
 Subscriber sur `telemetry` : **aucun message immédiat**. Le premier message arrive après ~2 s  
 (prochain tick du simulateur) avec `retain=False`.

 Si le simulateur reçoit un message de commande retained (cas de test) :  
 `{"event":"sensor.retained_ignored","topic":"campus/v1/devices/sensor-001/commands"}`  
 Le message retained est ignoré sans traitement.

Explication  
 La distinction `retain=True` / `retain=False` est volontaire :  
 - `state` et `availability` retained → permettent à tout nouveau subscriber (ex: backend qui  
   redémarre) de connaître l'état courant sans attendre le prochain tick.  
 - `telemetry` non-retained → un backend qui redémarre ne reçoit pas une ancienne mesure.  
   Il attend le prochain tick (2 s max) et a ainsi une mesure fraîche dès sa reconnexion.  
   Cela évite de mettre à jour `last_telemetry_at` avec un timestamp ancien et de masquer un  
   problème de staleness.

Décision  
 Comportement correct et conforme à ADR-04. Aucune modification nécessaire.

Vérification

- Premier message sur `state` : délai < 500 ms, `retain=True`
- Premier message sur `telemetry` : délai ≈ 2 s (prochain tick), `retain=False`
- Après redémarrage du backend : `isStale` devient `true` dans les 10 s si aucun tick n'arrive, non pas immédiatement

Observation  
 50 messages : +45 uniques en PG (5 doublons éliminés), latence API ~20 ms, sync en 1 cycle (5 s).  
 200 messages : +180 uniques en PG, sync en 1 cycle, latence API ~25 ms.  
 500 messages : +450 uniques en PG, sync en **1 cycle exact** (BATCH_SIZE=500), latence API ~35 ms.  
 1000 messages : +900 uniques en PG, sync en **2 cycles** (~10 s d'attente), latence API ~60 ms.  
 Aucun doublon métier à aucun niveau de charge.  
 Premier goulot identifié : **le cycle de synchronisation** — les 1000 messages arrivent  
 plus vite que BATCH_SIZE*2 ne peut les traiter en un seul cycle.

Explication  
 Le simulateur peut envoyer 1000 messages en < 2 s (limité par le réseau local et paho).  
 MongoDB les insère quasi-instantanément (opérations en mémoire + volume data < 1 MB).  
 Le job de sync (`syncBatch`) traite 500 messages par cycle toutes les 5 s.  
 Pour 1000 messages, il faut donc 2 cycles (10 s) avant que tous soient visibles dans l'API PostgreSQL.  
 La latence observée dans l'API augmente parce que `findHistoryByDevice` lit depuis PostgreSQL —  
 les mesures non encore syncées sont dans MongoDB mais pas encore dans la réponse API.  
 Le fallback MongoDB (`FallbackMeasurementRepository`) n'est activé que si PostgreSQL est  
 indisponible, pas pour les mesures en attente de synchronisation.

Décision  
 Goulot identifié et documenté. Comportement acceptable pour ce prototype.  
 Pour réduire la latence de visibilité : augmenter `BATCH_SIZE` ou réduire `SYNC_INTERVAL_MS`.  
 Pour tester au-delà de 1000 messages : augmenter le paramètre `count` jusqu'à 1000 (limite actuelle du simulateur).

Vérification

- 0 doublon métier à tous les niveaux de charge
- Latence API ≤ 100 ms pour 1000 messages (hors temps de synchronisation)
- Tous les messages (hors doublons éliminés) présents dans PostgreSQL après 2 cycles

## Jalons de fin de journée

- **Les 11 scénarios expérimentaux ont été exécutés avec une preuve reproductible.**
  - Isolation : 0 mismatch topic/deviceId sur 3 capteurs en parallèle
  - Usurpation : faille ACL wildcard documentée, mitigation per-device appliquée
  - Payload invalide : 4 cas rejetés sans crash, loggués dans Loki
  - Doublon : déduplication double (MongoDB + PostgreSQL) confirmée
  - Désordre/replay : état courant protégé par `ORDER BY observed_at DESC`
  - Capteur silencieux : `isStale=true` en ≤ 12 s, `isOnline` découplé
  - Broker indisponible : reconnexion automatique en ≤ 10 s
  - Backend indisponible : perte documentée avec `clean=true`, mitigation ADR-04
  - QoS 0 vs 1 : QoS 0 = perte certaine, QoS 1 = livraison garantie avec session persistante
  - Message retained : `state` retained, `telemetry` non-retained — comportement correct
  - Montée en charge : goulot = job de sync, 0 doublon à tous les niveaux

- **L'observabilité est centralisée dans Grafana + Loki.**
  - Tous les événements métier sont indexés et interrogeables en LogQL sans migration de schéma
  - Les requêtes de référence couvrent les 4 types d'anomalie : rejet, doublon, panne, charge

- **L'hygiène de sécurité est vérifiée.**
  - 0 secret dans Git, `.env.example` à jour, ACL Mosquitto per-device
